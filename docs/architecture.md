# AngioSight architecture and operating model

## Product scope

AngioSight is a local-first educational and research application. It accepts one user-entered clinical feature vector, estimates four binary model outcomes (CAD, LAD, LCX, and RCA), and displays those estimates beside a BodyParts3D anatomical reference. It does not create accounts, retain assessments, identify patients, localize lesions, provide clinical advice, or support care decisions.

The supplied dataset is small and is not evidence of clinical validity. The project must remain labeled research-only. Public clinical deployment is out of scope until independent clinical, privacy, security, and regulatory review is completed.

## Requirements and users

| Area | Current requirement and design |
| --- | --- |
| Primary users | Researchers, students, and hackathon demonstrators using de-identified or synthetic input. |
| Main workflow | Train locally → start API → open browser app → enter available inputs → request estimates → review model and holdout context → clear the assessment. |
| Platforms | Responsive browser app for desktop, tablet, and phone; WebGL is required for the interactive anatomy view. A native iOS/Android application is not included. |
| Persistence | No patient assessment database. Form values and predictions exist in browser memory for the current page session only. Dataset and trained artifacts are local files. |
| External integrations | None required. The Google Fonts import was removed so the UI does not contact a third-party font service. |
| Background work | Model training is an explicit offline command; inference runs synchronously in the API. No queues or scheduled jobs are needed for this dataset scale. |
| Analytics | None. Do not collect patient inputs, session replay, or advertising events. |
| Users/roles/auth | No accounts or roles in the local research deployment. The API is not an authenticated multi-user service and must not be exposed as one. |
| Database | None. Adding persistent records would change privacy, access-control, retention, backup, migration, and audit requirements and needs a separate design. |

## Technology choices

- **Web client:** React 18, Vite, Three.js, and React Three Fiber. Existing dependencies are retained; replacing the functioning client with Next.js would add migration risk without a server-rendering or routing requirement.
- **API:** FastAPI with Pydantic request validation and pandas/scikit-learn inference.
- **Model artifacts:** A trusted `joblib` bundle and JSON metadata generated by `python -m backend.train`. A bundle is loaded once when the API starts; restart the API after training.
- **Serving:** Vite proxy for local development; Docker Compose runs Nginx and the API on a private local network.
- **Deployment assumption:** Single-operator local/research environment. No public cloud or multi-tenant service is currently supported.

The 3D engine is split into its own production chunk and loaded when the viewer approaches the viewport. The browser first downloads the small assessment application; Three.js is intentionally larger than the general chunk budget because the anatomy view requires a WebGL renderer.

## Component and data flow

```text
Authorized local dataset
        │ explicit training command
        ▼
Preprocessing + four binary classifiers ──► models/bundle.joblib
        │                                   └► models/metrics.json
        │ trusted local files, read-only to serving container
        ▼
Responsive React app ── same-origin JSON ──► FastAPI
        │                                      ├─ schema/type/size checks
        │                                      ├─ in-memory model inference
        │                                      └─ request ID + sanitized errors
        ├─ anatomy mesh (static BodyParts3D reference)
        └─ results held in browser memory; no assessment is written to disk
```

### Training workflow

1. The operator confirms dataset permission, target meanings, and positive classes.
2. `backend.train` reads a local `.csv`, `.xlsx`, or `.xlsm` file.
3. Target columns are removed from predictors. Preprocessing is fit only on the training split; one random-forest pipeline is trained for each binary outcome.
4. The command writes `bundle.joblib` and `metrics.json` to the configured model directory. These files are trusted executable serialization artifacts; never load artifacts from an untrusted source.
5. The operator inspects class mappings and metrics, then restarts the API so it loads the new artifacts.

### Assessment workflow and edge cases

1. The browser requests `GET /metadata`. A missing API or untrained model is shown as a recoverable state; no placeholder estimates are produced.
2. The user can leave fields blank. The API creates a complete feature row in the exact training order, using `null` for missing inputs so the trained pipeline applies its fitted imputation.
3. The browser posts one JSON request. The API rejects malformed, nested, non-finite, wrongly typed, unknown, or oversized input before model inference.
4. The response returns all available target estimates and a research-use disclaimer. A failed model call returns a request ID and a generic message; request data and stack traces are not returned to the browser.
5. The user can clear inputs. Reloading also drops the in-memory form and result state.

## Storage and database design

There is no relational database or ORM because the current product does not persist accounts, assessments, or results. Assessment inputs and predictions stay in browser memory; the only browser-persisted value is the non-sensitive light/dark/system theme choice. Adding PostgreSQL now would create a sensitive health-data store without a user workflow that needs persistence. The dataset and model files are local, excluded from source control, and must be access-controlled and backed up according to the dataset's license and institutional requirements.

If persistence is later requested, pause implementation and first define user identity, explicit consent, purpose, data minimization, retention/deletion, tenant boundaries, audit needs, encryption and key management, backup/restore, migrations, and lawful basis. Only then design a schema and authorization model.

## API architecture

The browser uses same-origin `/api` paths; Vite and Nginx proxy them to FastAPI. The API's internal routes are:

| Method and path | Purpose | Data handling |
| --- | --- | --- |
| `GET /health` | Liveness/readiness status and whether a trusted model loaded. | No assessment data. |
| `GET /metadata` | Feature schema, dataset-level evaluation summaries, and the angiography branch metrics (when loaded). | No assessment data. |
| `POST /predict` | Estimate CAD, LAD, LCX, and RCA outputs for one feature map, with an optional angiography frame. | Processed in memory. If an image is sent it is decoded, scored, and discarded — never persisted or logged. Body limit is 6 MB. |

`POST /predict` accepts `{"features": {"Age": 52, "Sex": "Female"}}`, optionally with `"image": "<base64 PNG/JPEG>"` (or a `data:` URL). Omitted expected fields are treated as blank; unexpected feature keys are rejected. Numeric inputs must be finite JSON numbers. Categorical inputs must be strings. Booleans, arrays, objects, and oversized text values are rejected. Images must be PNG or JPEG and at most 5 MB decoded (6 MB request ceiling).

Successful responses use `{"predictions": {"CAD": {"probability": 0.0, "prediction": "...", "positive_class": "..."}}, "disclaimer": "..."}`. When an image is supplied the response also carries `imaging` (lesion probability, window count) and `fusion` (weights, frame AUC, basis), and `predictions.CAD.components` holds the separate tabular and imaging probabilities. Errors use `{"error": {"code": "...", "message": "...", "request_id": "..."}}`. The request ID is safe to include in a support report; never include patient values in a report.

OpenAPI docs are disabled by default. Set `ENABLE_API_DOCS=true` only in a trusted development environment.

## Security and privacy model

- The default API CORS origin is `http://localhost:5173`; configure an exact origin list only when needed. Credentialed CORS is disabled.
- The frontend sends no cookies or tokens. The API does not authenticate users; loopback development and the Compose private network are the supported trust boundaries.
- The API uses strict scalar request fields, a 6 MB body ceiling, numeric finiteness/type checks, PNG/JPEG magic-byte and size checks on any uploaded frame, an allowlist derived from the loaded feature schema, generic server errors, request IDs, and no-store/security response headers.
- Nginx limits request size (6 MB, to match the API ceiling) and inference frequency, sets browser security headers, and does not publish the API container port to the host.
- The Compose model mount is read-only. Only model artifacts created by a trusted local training run may be loaded.
- No assessment values are included in application logs. Do not enter identifiable health data. Local access logs should be handled as operational data and retained only as needed.
- Local network hosting is for a trusted Wi-Fi network. It is not HTTPS and is not a safe public deployment configuration.
- Images are static assets except for the optional angiography frame, which travels inside the `/predict` request, is scored in memory, and is never written to disk. The app has no user file storage, no image database, no payments, email, OAuth, WebSocket, or push-notification path.

This is not a production security certification. A public or clinical service would require a separate threat model, identity and authorization, TLS, managed secrets, infrastructure rate limiting, vulnerability and dependency review, monitoring/incident response, formal privacy review, and applicable clinical/regulatory approval.

## Deployment and configuration

### Local development

- Windows: `scripts/windows/setup.ps1`, then `scripts/windows/start-api.ps1` and `scripts/windows/start-web.ps1` in separate terminals.
- macOS/Linux: `bash scripts/unix/setup.sh`, then the corresponding `start-api.sh` and `start-web.sh` scripts.
- API binds to loopback. Vite binds to all interfaces to support testing from a phone on the same trusted Wi-Fi; firewall access to the web port should be temporary and limited to that network.

### Docker Compose

`docker compose up --build` serves the web app on port 5173; FastAPI remains inside the Compose network. A health check gates Nginx startup. The model directory is mounted read-only. Training happens outside the serving container. The Docker configuration is for private research/demo use and does not terminate TLS or provide user authentication.

### Environment variables

| Variable | Default | Meaning |
| --- | --- | --- |
| `MODEL_DIR` | `<project>/models` | Directory containing trusted `bundle.joblib` and `metrics.json`. |
| `ALLOWED_ORIGINS` | `http://localhost:5173` | Comma-separated exact browser origins allowed by CORS. |
| `ENABLE_API_DOCS` | `false` | Enables FastAPI Swagger/OpenAPI routes for trusted development only. |
| `VITE_API_URL` | `/api` in Docker; relative API path in Vite | Same-origin API prefix. |

Do not put dataset content, personal data, or credentials in environment files.

## Testing strategy

- **Unit:** Request shape and type checks, finite-number boundaries, missing/unknown inputs, positive-class mapping, probability bounds, and model metadata parsing.
- **API integration:** Health/readiness, metadata with and without artifacts, invalid request responses, prediction success/failure, and response security headers. Use temporary model directories and deterministic test doubles, never the real health dataset.
- **Frontend:** API offline/loading/success/error states, feature-group keyboard operation, clear/reset behavior, responsive form use, and no unintended persistence.
- **End-to-end:** Start API and web client with a temporary deterministic model; complete a full assessment at desktop, tablet, and phone viewport sizes; confirm failed inference remains recoverable.
- **Release checks:** Python unit tests, frontend production build, Docker build/compose health, manual keyboard/screen-reader review, dependency audit, and a check that `data/` and `models/` are not committed.

These checks assess software behavior only. They do not validate clinical performance.
